# ORIVANA — working rules (v2.0)

Frontend prototype of ORIVANA ("Personal Intelligence & Action Platform"). No backend yet; a typed mock layer stands in for the Go API.

Positioning (v2.0): ORIVANA keeps a researcher's **decisions** aligned with the evidence in their **own** papers, and acts on it with control. The UI leads with decisions and evidence, not with chat. Flagship feature: **Decision Impact**.

## Stack

`apps/web`: React 19 + TypeScript + Vite + Tailwind CSS v4 + shadcn-style components on Radix (`radix-ui`) + React Router 7 + TanStack Query + React Flow (`@xyflow/react`). Shared contract: `packages/contracts` (types + fixtures).

```
npm install          # root (npm workspaces)
npm run dev          # http://localhost:5173
npm run build        # tsc --noEmit + vite build
npm test             # vitest (service lifecycle tests)
node packages/contracts/scripts/generate-fixtures.mjs   # regenerate fixtures, then restart npm run dev
```

## Product rules (v2.0)

- **Knowledge tabs: Sources · Matrix · Claims · Map · Memory.** Map is the former Graph (same behaviour, plus an edge legend). Memory leads with decisions.
- **Within the user's collection only.** Search, answers, Matrix, and Claims use the user's uploads and Zotero items. No web search or paper discovery in the MVP.
- **Zotero is read-only.** Import and sync only; nothing is ever written back to Zotero. Say so in the UI wherever Zotero appears.
- **Every write needs approval.** External actions (GitHub issues) are proposals until the user approves them in Approvals; proposals from Decision Impact alerts follow the same flow and show their origin.
- **Model choice.** The answer model is chosen in Settings → Model preferences (`GET /models`, `PATCH /me/preferences`). Every answer shows **"Answered with <model>"**. Extraction and embedding models are system-managed.

## Status semantics (UI.md §2.3) — always text or an icon, never colour alone

| Meaning | Token | Required non-colour cue |
|---|---|---|
| Supports | `knowledge` | ✓ icon + "Supports" |
| Contradicts | `danger` | ✕ / opposing-arrows icon + "Contradicts" |
| Mentions | `fg-secondary` | "Mentions" label |
| Candidate | `warning` | dashed border/line + "Candidate" |
| Confirmed | `knowledge` | solid + "Confirmed" |
| Superseded | `fg-muted` | strike-through + "Superseded" |
| Needs review | `warning` | alert-triangle icon + "Needs review" |
| Gap (empty Matrix cell) | `subtle`, dashed | "No evidence" text on hover/focus and in list view |

Use `StatusBadge`, `OriginBadge`, and (v2) `ReviewStateBadge` / `SourceTypeBadge` rather than ad-hoc styles.

## Data rules (mandatory)

- No hard-coded content in components. Papers, messages, citations, entities, claims, matrix cells, decisions, alerts, models, proposals, events — everything dynamic — comes from JSON fixtures.
- `packages/contracts/types/` = one file per entity. `packages/contracts/fixtures/` = JSON per endpoint, generated by `scripts/generate-fixtures.mjs`; edit the generator, not the JSON.
- `apps/web/src/services/` = mock REST functions with simulated latency, errors (`{ code, message, details, request_id }`), and an in-memory store seeded from fixtures.
- Only `services/core/fixtures.ts` imports JSON. Components call hooks; hooks call services. Components never import JSON or the services' store.
- Assistant streaming is simulated SSE with events `status`, `token`, `citation`, `done`, `error`.
- **The API contract is additive only.** New endpoints, new optional fields, and new enum values may be added. Existing endpoint paths, request bodies, and response fields must not be renamed, removed, or change meaning. Record every addition in `docs/API-CONTRACT.md`; the Go backend implements that file exactly.

## UI rules (mandatory)

- UI text in English. Tagline and category exactly as in PRD. Never call the product "autonomous".
- No raw hex in components — use tokens (`bg-surface`, `text-fg-muted`, `border-control`, `text-knowledge`, …) defined in `src/styles/index.css`.
- Primary buttons: `on-accent` text (#0B0D12) on `accent` (#8B9CFF). Never white on the accent.
- Actions are `<button>`; navigation is `<a>` / `Link` (`ButtonLink` for button-styled links).
- Every interactive element is keyboard reachable with the visible focus ring (2 px accent, 2 px offset). The Matrix supports arrow-key navigation between cells.
- Components ≈ 200 lines max; split larger ones.
- Never show success before the mock service confirms it (no optimistic "Succeeded"; approvals show Executing until `verified_at`).
- Column budget: at 1440 px never more than three full columns; screens that need more (Assistant, Map, Document viewer, Matrix/Claims with inspector when needed) collapse the app sidebar to the 64 px rail.
- Loading, empty, and error states for every async view, including every new v2 screen.
- Mobile never forces a dense graph or a wide table: Map → list, Matrix → list grouped by method, Claims → cards.
- Do not break existing screens. Renamed routes keep a redirect (e.g. `/knowledge/graph` → `/knowledge/map`).
